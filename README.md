# Harflex

Harness desktop local-first em Go + Wails v3 e React, orientado a sessões de agentes e evidências SDD. O aplicativo implementa catálogo SQLite, cofre do sistema, journal de eventos, provedor OpenAI compatível, adaptadores CLI e ferramentas com política de aprovação. As 17 áreas do menu têm ações próprias, incluindo pipelines SDD, agentes, skills, MCP, workflows, Git, worktrees, agendamentos com o app aberto, canais por pasta local e busca textual no conhecimento do projeto. O [plano do produto](PRODUCT.md) registra recursos mais profundos ainda pendentes; esta versão não afirma paridade integral com Pi ou LionClaw.

## Desenvolvimento local

Pré-requisitos: Go com toolchain preferencial 1.26.8, Node 22/npm, dependências nativas da plataforma e Wails **v3.0.0-beta.26**. O módulo mantém `go 1.25.0`; `toolchain go1.26.8` sugere uma toolchain, não fixa exatamente o compilador nem substitui atualizações de segurança. Confira a versão efetiva com `go version`.

### Atalhos com Make

Em macOS/Linux ou Windows com GNU Make e shell POSIX (Git Bash/WSL), use `make help` para listar os alvos. O Makefile compila o CLI Wails fixado em `go.mod` para `bin/` (ignorado pelo Git); não requer `wails3` ou `task` global.

```bash
make setup
make setup-e2e        # uma vez, para Playwright
make dev
make test             # Go -race, frontend e Playwright
make check            # também tidy, diff e release gates
make build            # app da plataforma atual
make package          # pacote da plataforma atual
make installers       # instaladores: .dmg no macOS, .exe NSIS no Windows, AppImage/deb/rpm no Linux
```

Para rodar `make dev` ao lado do app instalado (ou de outro worktree) sem tocar nos dados reais, aponte um diretório próprio: `HARFLEX_DATA_DIR=/tmp/harflex-dev make dev`. O catálogo SQLite, o diretório privado do Code, as cópias de execução do Code de pipeline e o lock de instância única passam a depender desse diretório; sem a variável, o comportamento é o de sempre (`<config do usuário>/Harflex`). Para explorar a interface no navegador com o backend Go real (por exemplo, para automação), compile com `go build -tags server -o bin/harflex-server .` e rode com `FRONTEND_DEVSERVER_URL=http://127.0.0.1:9245 WAILS_SERVER_PORT=9246 HARFLEX_DATA_DIR=... bin/harflex-server` ao lado de `npm run dev -- --port 9245`; diálogos nativos (escolher pasta/arquivo) só existem no app desktop.

Use `make build TARGET_OS=windows` (ou `linux`/`darwin`) somente com as dependências/cross-compilação da plataforma configuradas. `make package` no macOS aplica a assinatura ad hoc local definida no Taskfile; não faz assinatura Developer ID, notarização, push nem publicação. Build/package podem regenerar bindings, ícones ou arquivos de módulo rastreados; confira `git status` e o diff após executá-los. Em PowerShell sem shell POSIX, use os comandos `wails3`/Taskfile abaixo.

`make installers` gera os instaladores da plataforma atual, ou de `TARGET_OS`:
- **macOS:** `bin/harflex.dmg`, com o app e o atalho para Aplicativos. A arquitetura é a desta máquina; `UNIVERSAL=1` gera um único `.dmg` para Apple Silicon e Intel. A assinatura é ad hoc, sem Developer ID nem notarização, então em outro Mac a primeira abertura pede clique direito > Abrir.
- **Windows:** `build/windows/nsis/harflex-installer.exe`, que precisa do `makensis` (`brew install makensis` no macOS).
- **Linux:** AppImage, `.deb`, `.rpm` e pacote AUR em `bin/`.

O ícone fica em `build/appicon.png` (o `.icns` e o `.ico` saem dele com `wails3 generate icons`) e em `build/appicon.icon` (formato do Icon Composer). O app usa o `.icns`: o `Assets.car` do formato novo do macOS precisa do Xcode completo (`actool`) para ser gerado, por isso o `Info.plist` não declara `CFBundleIconName`.

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-beta.26
cd frontend
npm ci
cd ..
wails3 dev
```

Inclua o diretório de instalação de binários Go no PATH: o valor de `go env GOBIN`, se definido, ou `bin` dentro de `go env GOPATH`. Não há dependência de caminhos absolutos da máquina de desenvolvimento. No PowerShell, use `$env:PATH` para acrescentar esse diretório. A action setup-go já o inclui nos runners.

macOS requer Xcode Command Line Tools. Windows requer WebView2 para executar o app. No Ubuntu 24.04, instale `build-essential pkg-config libgtk-4-dev libwebkitgtk-6.0-dev`, conforme [Wails](https://v3.wails.io/getting-started/installation/) e o doctor da versão fixada. `wails3 doctor` verifica dependências locais.

## Verificação e build

```sh
wails3 task test:go
wails3 task test:frontend
wails3 task check:tidy
wails3 task check:diff
node --test scripts/release-gates.test.mjs
cd frontend
npx playwright install chromium
npm run test:e2e
cd ..
wails3 build
```

`wails3 task check` agrega os gates após instalar dependências e navegador. Para usar Chrome instalado, defina `PLAYWRIGHT_CHANNEL=chrome` no ambiente. Em PowerShell: `$env:PLAYWRIGHT_CHANNEL = 'chrome'`; em bash/zsh: `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`. Sem a variável, Playwright usa seu Chromium. `test:e2e` no Taskfile ativa CI e usa a porta 9345 por padrão; defina `HARFLEX_E2E_PORT` para isolar worktrees simultâneos.

`check:diff` verifica mudanças locais e, quando `origin/main` está disponível, todos os commits desde o merge-base. Sem o remote, execute `git diff --check <base-local>..HEAD` com o commit base da sua branch. Na CI, o gate usa a base da PR ou o commit anterior ao push; sem esse commit, usa o merge-base com o branch padrão ou compara o snapshot inteiro com uma árvore vazia.

Ao abrir, o app reabre o projeto usado por último (o catálogo lista o mais recente primeiro); se a pasta não existir mais, a tela de abertura oferece os projetos recentes. A lista de sessões usa uma prévia da primeira mensagem como título e recolhe as sessões internas do SDD. Nas conversas, as respostas do agente são renderizadas como Markdown sem HTML bruto (links só `http(s)`/`mailto`, nenhuma imagem remota é buscada), aprovações mostram o conteúdo que será gravado ou o comando completo antes da decisão e o compositor fica sempre visível.

Os E2E em 320×720, 768×1024, 900×700 e 1440×900 usam uma fachada **sintética**. Não chamam provedores, shell, arquivos reais ou Wails. A fixture `foundation` persiste apenas journal sintético em sessionStorage e devolve o mesmo ID após reabrir o setup, exercitando replay depois de reload. A UI lista e reabre sessões; esses testes validam o fluxo visual e o replay, sem comprovar retomada em um CLI real. Screenshots e relatórios ficam em `frontend/test-results` e `frontend/playwright-report`, ignorados pelo Git. O navegador comum sem fixture informa backend indisponível.

## Agendamentos locais

Agendamentos diários ou de execução única guardam fuso IANA e horário local no SQLite. O próximo disparo é calculado no fuso escolhido; um horário diário inexistente por mudança de horário de verão é pulado, e um horário inexistente ou ambíguo de execução única é recusado. Cada job executa um prompt ou os passos de um workflow e registra estado, erro seguro e vínculos de sessão/workflow. Um job que aguarda aprovação humana não é concluído automaticamente; após a decisão, o scheduler reconcilia a sessão e continua as etapas restantes enquanto o app está aberto. Só um job ativo por agendamento é admitido; o disparo manual é permitido mesmo com o agendamento pausado. A tela mostra os 200 jobs mais recentes por projeto.

**O aplicativo precisa estar aberto para disparar jobs.** Não há serviço de sistema operacional, inicialização em segundo plano nem execução com o aplicativo fechado. Ao reabrir, a política “Ignorar” grava um job ignorado para o horário perdido; “Executar uma vez ao reabrir” colapsa os horários perdidos em um job. Enquanto o aplicativo está aberto, atrasos superiores a um minuto também são considerados perdidos pela política “Ignorar”. Jobs iniciados antes de um encerramento inesperado são marcados como interrompidos e não são repetidos automaticamente, pois podem ter produzido efeitos. Cancelar um job ativo registra uma solicitação até o resultado do filho ser confirmado; uma falha nessa solicitação fica visível e não declara o job cancelado. Ao fechar normalmente, o scheduler solicita cancelamento e aguarda o job ativo antes de fechar o SQLite.

Agendamentos com backend CLI exigem consentimento explícito no formulário: o CLI executa com a autoridade do seu próprio processo e a política de ferramentas do Harflex não controla suas ações internas. A definição do prompt fica salva no catálogo local; evite inserir credenciais no texto.

## Delegação de subagentes

Uma delegação parte da sessão atual e cria um filho com snapshot do agente e backend escolhidos. Filho, vínculo com o pai, tarefa redigida e evento de journal são gravados em uma única transação; falha no registro não deixa sessão órfã. A árvore mostra só uma prévia de até 280 caracteres, e o texto completo permanece no journal local. A interface gera um ID aleatório por tentativa e guarda somente esse token no armazenamento local até confirmar a resposta. Repetir a tentativa com o mesmo ID, pai, agente e tarefa retorna o filho já registrado, inclusive após reinício; reutilizar o ID com tarefa ou agente diferente é recusado. Nesse caso o Harflex abre o histórico, mas **não executa novamente**: se a tarefa ainda não começou, use “Preparar tarefa delegada” para colocá-la no rascunho e revise antes de enviar. Uma tarefa ainda não iniciada permanece visível na árvore de agentes após reinício. Se a redação ocultou um segredo, complete o texto antes de enviar. Após confirmação, uma nova ação “Delegar” recebe outro ID e pode executar intencionalmente a mesma tarefa em outro filho.

Cada filho aceita no máximo três tentativas admitidas de `Prompt`, reservadas no SQLite antes de entregar a chamada ao runner; uma queda, falha ou cancelamento após a reserva consome a tentativa. Rejeição por sessão ocupada ou backend não retomável compensa a reserva. O contador permanece após reinício. Cada trecho ativo de `Prompt` ou `Approve` recebe um prazo de cinco minutos, aplicado também ao processo Codex/OpenCode via cancelamento do contexto. A espera pela decisão humana entre trechos não consome esse prazo; portanto cinco minutos **não** é duração total máxima de um turno com aprovações. O loop Go ainda limita uma execução a 50 rodadas e 64 chamadas de ferramenta por resposta. Esses limites não são teto de custo ou tokens, não revertem efeitos já feitos e não restringem ações internas de um CLI antes do cancelamento. A interface mostra contador, limite e prazo tanto na árvore quanto na conversa do filho.

A prévia persistida remove apenas credenciais conhecidas pela sessão no momento da criação. Ela não detecta segredos arbitrários digitados na tarefa; revise o texto antes de delegar, especialmente ao usar provedores remotos ou CLIs. Para conferir retries divergentes, o SQLite local também guarda um SHA-256 do prompt original: esse hash não é enviado à UI, mas quem já pode ler o banco pode testar palpites de tarefas curtas ou previsíveis. Proteja o diretório de dados do usuário.

O vínculo com o pipeline SDD do pai ainda não é herdado formalmente pelo filho: a árvore permite voltar à sessão pai, mas a conversa do filho não aparece como sessão de etapa nem alimenta automaticamente a avaliação do pipeline. Revise e anexe suas evidências à etapa apropriada.

## Canais locais

Em **Canais**, configure uma pasta relativa ao projeto aberto, por exemplo `channels/equipe`. O Harflex cria `inbox/` e `outbox/` sob ela. Coloque arquivos `.txt` ou `.md` na inbox e escolha **Importar inbox** para registrar as mensagens; escreva uma resposta e escolha **Enviar resposta** para publicar um `.md` na outbox. Nenhuma dessas ações ocorre em segundo plano, e o canal não usa rede ou credenciais.

Cada leitura aceita até 500 entradas por importação e 64 KiB de texto UTF-8 por arquivo. Se a inbox ultrapassar esse limite, mova, organize ou remova manualmente arquivos da pasta antes de importar novamente; o Harflex nunca apaga os originais. A interface apresenta as 500 mensagens mais recentes; o histórico completo permanece no SQLite. A mesma fonte sem mudança não duplica o registro. Um envio recebe um ID estável por rascunho e canal: após falha, repetir a ação confere a mesma saída e nunca sobrescreve um conteúdo diferente. O rascunho só é limpo após a entrega aparecer na releitura do histórico.

## Worktrees

**Worktrees** (menu Contexto) lista todas as pastas de trabalho do repositório do projeto aberto e julga cada uma. **Pode excluir** só aparece quando o worktree está limpo (sem alterações nem arquivos novos), sem commits que a branch base não tenha, sem operação de Git em andamento, sem trava, sem nenhum programa usando a pasta (terminal, editor, servidor de desenvolvimento, sessão de agente ou o próprio Harflex rodando dali) e quando não é o worktree principal nem o projeto aberto. Em qualquer outro caso aparece **Não pode excluir** com os motivos: alterações não salvas, commits ainda não mesclados, HEAD destacado com commits soltos, pasta ausente, travado, merge ou rebase em andamento. O mesmo controle aparece no cabeçalho do projeto, em todas as telas: branch, o que está pendente, o veredito e os atalhos. Em **Todos os projetos**, a página mostra os worktrees de todos os projetos ativos (sem os arquivados), um grupo por repositório; projetos que são worktrees do mesmo repositório entram no mesmo grupo. As ações de cada grupo passam pelo projeto que representa o repositório, e o worktree do projeto aberto nunca é oferecido para exclusão ali. A checagem de programas em uso roda uma vez para todos os repositórios.

Para um worktree com trabalho pendente, **Salvar e mesclar com a IA…** primeiro guarda uma cópia de segurança do que está lá (um commit sob `refs/harflex/worktree-saves/…`, feito sem tocar em arquivos, índice ou branch do worktree), depois abre uma conversa no projeto principal e pede à IA que commite o pendente e mescle a branch na base. A conversa passa a ser o projeto aberto, e cada comando segue a política de aprovação normal. A IA não exclui nada: quando a execução termina, o Harflex julga o worktree de novo e só remove a pasta (e a branch já mesclada, se pedido) se tudo estiver salvo e mesclado e a opção “Excluir o worktree quando tudo estiver salvo e mesclado” estiver marcada. Se ainda restar algo, nada é excluído e o aviso diz o que falta; **Conferir agora** repete a checagem, e continuar a conversa com a IA faz o Harflex conferir de novo quando ela terminar. No modo Casual o aviso aparece na própria conversa.

Limites. A exclusão nunca usa `--force`, e o backend julga de novo no momento de excluir, recusando o que mudou desde a lista. Itens ignorados pelo Git (como `node_modules/` ou `.env.local`) não estão em nenhum commit e só são apagados com confirmação explícita. A cópia de segurança inclui arquivos novos que o Git não ignora, mesmo um `.env` esquecido fora do `.gitignore`, e fica só no repositório local; a IA é instruída a não commitá-los. O Salvar com a IA exige que o worktree principal esteja limpo, porque a mescla acontece nele. Quando ele tem alterações, o próprio worktree principal oferece **Commitar com a IA**: depois da cópia de segurança, a IA só commita as alterações na branch base, sem mesclar, trocar de branch nem apagar nada, e o Harflex confere se não sobrou nada pendente. Isso libera os outros worktrees. Um CLI como backend da IA só é aceito com modelo padrão salvo em Configurações e confirmado pelo catálogo; provedores por API não têm essa exigência. A checagem de programas em uso procura processos cujo diretório de trabalho ou linha de comando está na pasta (`lsof` e `ps` no macOS, `/proc` no Linux), custa cerca de um segundo por leitura e não existe no Windows, onde o sistema recusa a remoção de uma pasta aberta. Worktrees travados (`git worktree lock`) só se liberam manualmente, e a limpeza de registros de pastas ausentes (`git worktree prune`) deixa os travados em paz.

## Conversas no modo Casual

A barra lateral do Casual mostra as conversas de todos os projetos ativos, agrupadas por projeto, como no Codex: o projeto aberto em cima, com a lista completa e a busca, e os outros projetos abaixo, cada um com as conversas mais recentes. Abrir uma conversa de outro projeto troca de projeto antes. Cada conversa pode ser fixada; as fixadas ficam numa seção própria no topo, com o nome do projeto. No cartão da mensagem, ao lado do controle de permissões, uma pílula com o nome do projeto troca de projeto num clique; na tela de novo chat, o que já foi digitado vai junto. Cada projeto tem **Abrir a pasta** (no Finder, no Explorer ou no gerenciador de arquivos) e, nos outros projetos, **Novo chat** naquele projeto.

## Terminal no painel lateral

O botão de sol ou lua no cabeçalho alterna entre o tema claro e o escuro. A escolha fica salva neste computador; sem escolha, o app segue o tema do sistema. O terminal continua escuro nos dois temas.

Um ícone no canto do cabeçalho abre e fecha o painel lateral, que tem as abas **Atividade** e **Terminal** e lembra a última usada. O terminal é o seu shell (`$SHELL -l`, com `TERM=xterm-256color`) aberto na pasta do projeto, sob a sua conta, sem sandbox: não é um agente. Ele só abre na primeira vez que a aba é mostrada, continua rodando quando o painel fecha ou a aba muda, e redesenha a saída recente (até 2 MiB) ao voltar; **Novo terminal** encerra o atual e abre outro. A saída chega por evento (`harflex:terminal`), em base64 para não partir caracteres; o shell termina junto com o app. No Windows o terminal ainda não é suportado.

A fase **QA** é um laboratório. O QA roda as verificações do projeto de verdade: instalação, build, testes unitários, E2E e o app no ar. Ele trabalha numa cópia só dele, feita a partir da cópia do Code, com terminal e rede e sem pedir aprovação a cada comando; nada do que ele instala ou gera vai para o patch. O relatório traz:
- as verificações, com o comando e o resultado de cada uma;
- as **falhas**, que já vêm marcadas;
- as **melhorias sugeridas**, que você marca se quiser.

**Corrigir os selecionados** manda os itens marcados (e uma observação opcional) de volta ao Code, que continua na mesma cópia. A partir daí o ciclo roda sozinho em segundo plano: o Code corrige, a correção é aprovada pelo ciclo e o QA roda de novo. Ele se repete enquanto houver falhas, até três rodadas de correção, e para quando o QA passa. Se o modelo terminar sem o relatório, o ciclo pede o relatório de novo na mesma conversa.

Na fase **PRs**, **Aprovar e abrir os PRs** aplica o patch aprovado e abre o chat que cria a branch, faz o commit, o push e o PR. Cada PR aberto é registrado e aparece num card, com link, branch, estado e uma linha do tempo. Com **Vigiar revisão** ligado, a cada 10 minutos o mesmo chat:
- lê os comentários novos de revisão;
- corrige no mesmo branch, roda os testes e faz push;
- responde cada comentário.

A vigia nunca faz merge nem force push e para quando o PR é mergeado ou fechado. Ela precisa de Acesso total no projeto; sem isso, o card avisa e oferece o seletor de permissões.

O agente das conversas sabe que está no Harflex, seja qual for o motor (modelo de API, Codex ou Claude Code). Ele recebe instruções sobre a plataforma: modos Casual e Professional, as fases do SDD e quem aprova cada uma. Essas instruções chegam ao Codex como `developer_instructions` e ao Claude Code como `--append-system-prompt`, a cada turno, então valem também para conversas antigas. A configuração global dos CLIs (`~/.codex`, `~/.claude`: skills, AGENTS.md, MCPs) continua valendo, mas o Harflex tem prioridade quando há conflito.

Nas conversas, o agente tem três ferramentas do Harflex, sempre restritas ao projeto da conversa:
- `harflex_create_pipeline` cria um pipeline SDD com o Discovery combinado no chat;
- `harflex_list_pipelines` lista os pipelines do projeto;
- `harflex_get_pipeline` lê um pipeline, com fases, status e, se pedido, os documentos.

Aprovar e avançar fases continua sendo da pessoa, na tela Pipelines. Quando o agente cria um pipeline, aparece um aviso no canto com o botão **Abrir**.

Os modelos de API recebem essas ferramentas diretamente. O Codex e o Claude Code as recebem por um servidor MCP local do Harflex:
- ele escuta só em `127.0.0.1`, recusa navegadores e cada conversa tem um token próprio;
- o token chega ao CLI pela variável `HARFLEX_MCP_TOKEN`, nunca pelos argumentos;
- no Codex, só as ferramentas do Harflex são pré-aprovadas.

A aba **Atividade** desenha o último pedido como um fluxo ([React Flow](https://reactflow.dev)): o pedido no topo, as etapas do plano na espinha (feita, agora, pendente) e, ramificadas de cada etapa, as ações com texto, como "Lendo validate.ts", "Escrevendo style.css" ou "Rodando um comando" com o comando abaixo. Cada ação mostra se está na fila, em andamento, aguardando aprovação, feita ou com falha, e o fluxo termina no resultado. A câmera acompanha o que está acontecendo até você mover o canvas; **Acompanhar** volta a seguir. O plano vem de três fontes:
- da ferramenta `update_plan`, que os agentes de API recebem nas conversas e no Code das pipelines (inclusive agentes com lista restrita de ferramentas, porque ela não altera nada);
- da lista de tarefas do Codex;
- do checklist Markdown (`- [ ]` / `- [x]`) que o Claude Code é instruído a publicar, porque no modo `-p` ele não tem ferramenta de plano. Quando ele só republica o checklist no fim, cada ação vai para a etapa iniciada que cita o arquivo dela.

Sem plano, as ações ficam penduradas no pedido. Erros brutos das ferramentas continuam só na conversa. O painel lateral tem largura ajustável: arraste a borda esquerda, ou use as setas no separador; o duplo clique volta aos 360 px. A largura fica salva neste computador e é limitada enquanto a janela for estreita.

## Memória do projeto

Ao abrir um projeto que nunca foi lido, o Harflex pergunta se a IA deve lê-lo; com um sim, ela lê o que ele já tem e o Harflex guarda o resultado como a memória do projeto, para que Discovery, SPEC e Plan já conheçam as tecnologias, os domínios, os repositórios e os serviços sem que a pessoa precise explicá-los. A coleta é feita pelo próprio Harflex, sem IA: READMEs, `AGENTS.md`, `CLAUDE.md`, `docs/**/*.md`, manifestos (`go.mod`, `package.json`, `pom.xml`, `build.gradle`, `template.yaml`, `Dockerfile`, OpenAPI e AsyncAPI, workflows do GitHub e outros), as duas primeiras camadas de pastas e os repositórios Git dentro do projeto, com remoto (sem usuário nem senha) e branch. O guia e os manifestos de cada repositório entram antes de qualquer documento mais fundo. Cada arquivo é cortado (8 KiB na raiz, 3 KiB nas pastas) e o total fica em 120 KiB. Pastas pesadas (`node_modules`, `dist`, `build`, `.git`, worktrees) e qualquer arquivo com cara de segredo (`.env*`, chaves, certificados, nomes com token, secret, credential ou password) nunca são lidos.

A IA que escreve a memória é a mesma da fase Discovery (a escolha do projeto em Pipelines ou o padrão das Configurações), pelo mesmo caminho isolado dos documentos: sem ferramentas e com os arquivos como dados. O resultado tem seções fixas (Visão geral, Tecnologias, Domínios, Repositórios, Serviços, Convenções e documentos-chave) e cabe em 64 KiB. A página **Memória** (menu Contexto) resume a memória do projeto aberto: quantas tecnologias, domínios, repositórios e serviços a IA encontrou, a visão geral em destaque, os domínios e repositórios como etiquetas, cada seção completa e os arquivos lidos, com Editar e Ler de novo. Em Projetos, cada card mostra o estado da memória (lendo, pronta, sem IA escolhida ou falha), com **Ver memória**, **Editar** e **Ler de novo**. Uma versão editada vale até uma nova leitura pedida. Uma leitura que falha mantém a memória anterior. Nada é lido sem essa confirmação. **Agora não** fica registrado e o projeto não pergunta de novo; a leitura continua a um clique em **Ler o projeto com a IA**, no card do projeto ou na página Memória. Nas fases de documento, a memória pronta vai no campo `projectMemory` do pedido. Uma conversa nova (API ou CLI) também começa com a memória nas instruções, guardada junto com as skills da sessão: reabrir a conversa depois mantém a memória com que ela começou, e uma conversa criada antes da leitura não a recebe. O Codex não tem opção de prompt de sistema, então as instruções do Harflex (memória, skills e o agente escolhido) vão à frente da primeira mensagem de cada conversa nova.

## Conhecimento local

Arquivos `.txt`, `.md` e `.markdown` dentro do projeto podem ser indexados em chunks FTS5, reindexados ou removidos apenas do índice. Os resultados e a ferramenta `knowledge_search` do agente mostram caminho, linha, trecho e horário da fonte. O índice permanece nesta máquina; se o agente usar a ferramenta com um provedor de IA externo, o trecho retornado pode seguir para o endpoint configurado.

Cada projeto pode salvar um perfil de embeddings para Ollama (`/api/embed`) ou LM Studio (`/v1/embeddings`) com URL HTTP de IP de loopback e identificador de modelo. Salvar o perfil não conecta, baixa ou inicia modelos. O botão de indexação envia no máximo oito trechos por chamada ao servidor local escolhido; cada lote é salvo em SQLite e pode ser retomado após interrupção ou reinício. A busca combina FTS e vetores quando ambos retornam resultados, indica busca semântica quando só vetores retornam e informa fallback textual quando os vetores estão indisponíveis. Trocar o perfil deixa os vetores antigos fora da busca ativa. A UI e `knowledge_search` expõem o modo da resposta. Para índices acima de 10.000 vetores, a consulta vetorial é limitada e a busca continua em modo textual.

A indexação automática iniciada pela tela de Conhecimento depende de a tela permanecer aberta. Ao sair, a parada aguarda no máximo o lote ativo de até 30 segundos; os lotes concluídos ficam em checkpoint no SQLite para continuação, sem recomeçar do zero.

A CI define testes e smoke builds nativos de macOS, Windows e Linux; uploads `unsigned-smoke-*` são apenas artefatos de inspeção. Configuração versionada não comprova execução hospedada. Build local macOS não prova execução Windows/Linux. Não há publicação, assinatura de distribuição, deploy ou distribuição remota neste fluxo.

Na conversa livre, o Codex lista modelos dinamicamente pelo app-server local. Modelo e esforço são escolhidos após consulta explícita; “Automático” omite o parâmetro de esforço. A escolha é salva de forma atômica com a sessão e relida antes de cada prompt. Revisões de executável, diretório, arquivos locais conhecidos, configuração efetiva e conta do app-server são comparadas; divergência impede a execução. O catálogo não concede aprovação de ferramentas. Perfis HTTP continuam com escolha de modelo no próprio perfil; a seleção herdada por fase SDD ainda está em implementação.

OpenCode permanece **indisponível por padrão**: a flag `--pure` e o binário nativo são verificados, mas a prova positiva de que plugins seriam carregados sem ela exige um ambiente realmente isolado, não a configuração pessoal do usuário. Nenhuma integração padrão é anunciada como segura antes desse atestado. A injeção de caminho explícito existe para testes/ambientes controlados, não equivale a uma liberação de distribuição.

O Claude Code é o terceiro CLI. O Harflex procura nos lugares de instalação usuais (`~/.local/bin`, `/opt/homebrew/bin`, `~/.claude/local`, o `PATH`) e, no macOS, na cópia que o app Claude mantém em `~/Library/Application Support/Claude/claude-code/<versão>/`, a mais nova primeiro. Na conversa ele roda em `claude -p --output-format stream-json`, com o prompt pela entrada padrão, edições aceitas dentro do projeto (`--permission-mode acceptEdits`; o que pediria outra permissão é recusado, porque ninguém responde no modo não interativo), as instruções do agente acrescentadas ao prompt de sistema e `--resume` para continuar a conversa. O Claude Code não tem comando que liste modelos: o catálogo oferece os apelidos `fable`, `opus`, `sonnet` e `haiku`, que sempre apontam para o modelo mais novo de cada família, com os cinco níveis de `--effort`, e só depois de `claude auth status` confirmar o login. Sem login, a tela diz isso. A escolha fica presa às configurações do CLI (`settings.json` do usuário, as gerenciadas e as `.claude/settings*.json` do projeto), não ao `~/.claude.json` nem às credenciais, que mudam a cada execução.

Nas fases do SDD (Discovery, SPEC, Plan, Code e QA) o Claude Code trabalha como o Codex: só como modelo. Cada chamada roda numa pasta temporária, sob o `sandbox-exec` do macOS, com `--tools ""`, `--setting-sources ""`, `--strict-mcp-config`, `--disable-slash-commands` e `--no-session-persistence`, o prompt de sistema do Harflex no lugar do padrão e a resposta presa a `--json-schema`. O sandbox impede a leitura do `CLAUDE.md` e das `rules` pessoais. Se a CLI anunciar qualquer ferramenta além da `StructuredOutput` que o próprio schema cria, ou qualquer servidor MCP, a fase falha. As ferramentas de leitura e escrita do Code e do QA continuam sendo as do Harflex, limitadas à cópia isolada. O login do Claude Code fica no Keychain, salvo pelo `USER`, então essa variável é a única a mais que o processo recebe. Como os modelos Claude preferem chamar ferramentas diretamente, o prompt de sistema diz que só a `StructuredOutput` existe e que as ferramentas do Harflex vão dentro de `toolCalls`; uma tentativa direta é recusada pela própria CLI e não encerra a fase. Uma atualização do Claude Code invalida a escolha feita para a versão anterior; basta consultar os modelos de novo.

## Permissões do projeto

Cada projeto tem um perfil de permissões, que vale para todas as conversas dele, inclusive as já abertas: a troca é lida de novo a cada chamada de ferramenta. Escolha no menu **Permissões do projeto**, logo acima da caixa de mensagem, ou em Configurações:

- **Perguntar**: escrita, shell e ferramentas de rede (inclui MCP) pedem a sua aprovação.
- **Workspace confiável**: escrita na pasta do projeto liberada; shell e rede continuam pedindo.
- **Acesso total**: nada pede aprovação. O agente cria e edita arquivos, roda comandos e chama ferramentas MCP sozinho. Ativar exige uma confirmação, o backend só aceita o perfil com `confirmFullAccess`, e o menu mostra o aviso “Sem pedir aprovação” enquanto ele estiver ligado. Pedidos que já estavam esperando continuam esperando a sua resposta. O perfil é do projeto, então agendamentos, workflows e subagentes dele também deixam de pedir aprovação, mesmo rodando sem ninguém por perto.

As ferramentas de arquivo continuam confinadas à pasta do projeto em todos os perfis, mas o terminal, os CLIs externos e os servidores MCP locais rodam com os seus privilégios e não são sandbox (veja Segurança e limites): em Acesso total, nada impede um comando de ler ou alterar fora da pasta. Acesso total é a escolha para deixar o agente trabalhar sem interrupções, por exemplo para abrir pull requests.

## Servidores MCP prontos

Em **MCP Servers**, **GitHub** e **Bitbucket** já aparecem configurados; falta só a credencial. **Salvar e conectar** guarda o token no cofre do sistema, valida a conexão e liga as ferramentas para as próximas conversas do projeto. Se a conexão falhar, o servidor fica salvo e desativado e a tela diz o que conferir; **Conectar** tenta de novo sem digitar a credencial outra vez.

- **GitHub** usa o servidor remoto oficial (`https://api.githubcopilot.com/mcp/`) com um token de acesso pessoal enviado como `Bearer`. Token clássico com escopo `repo`, ou token granular com leitura e escrita em Contents e Pull requests.
- **Bitbucket** usa o servidor Rovo MCP da Atlassian (`https://mcp.atlassian.com/v2/mcp`) com o e-mail da conta e um token de API com escopos, enviados como `Basic` (`e-mail:token` em base64). O token precisa dos escopos `read:bitbucket:agent-interface` e `write:bitbucket:agent-interface`; o administrador da organização precisa liberar a autenticação por token de API (Atlassian Administration, Rovo, Servidor MCP, Autenticação; vem desligada) e o workspace do Bitbucket precisa estar vinculado a uma organização Atlassian. A página “Interacting with Bitbucket via MCP” descreve outro servidor, embutido nos passos de agente do Bitbucket Pipelines, que não tem endereço externo.

O formulário de servidor próprio também escolhe como enviar a credencial (`Bearer` ou `Basic usuário:token`). Cada chamada de ferramenta MCP segue as permissões do projeto. Quando um servidor recusa uma chamada (branch que já existe, pull request já aberto, campo faltando), a resposta dele volta ao modelo como falha da ferramenta e a execução continua, para o agente corrigir e tentar de novo.

## Provedor e modelo por fase

Na página **Pipelines** há o cartão **Provedor e modelo por fase**. Ele fica aberto enquanto o projeto ainda não tem pipeline e se recolhe quando o primeiro nasce (abra-o quando quiser). Lista Discovery, SPEC, Plan, Code, QA e PRs; em cada fase você escolhe um provedor de API ou o Codex e o modelo. **Fase sem escolha segue o padrão das Configurações.**

- **Vale para o projeto.** O próximo trabalho e as fases que ainda não rodaram usam o que estiver ali. A escolha fica no catálogo (tabela `workspace_stage_executors`, migração 050) só com identificadores, executor e modelo: o catálogo de modelos é consultado de novo quando a fase roda, então um modelo que saiu dele é percebido ali, e não aceito em silêncio.
- **Escolha completa.** Um perfil de API vale sozinho (sem modelo, usa o do perfil); um CLI só é gravado com um modelo.
- **O que cada fase aceita.** Discovery, SPEC, Plan, Code e QA aceitam perfis de API com catálogo (não os genéricos), o Codex e o Claude Code quando o Harflex consegue prendê-lo ao contrato da fase. Os PRs aceitam só perfis de API, porque o terminal e o MCP rodam no Harflex (um servidor genérico só entra nos PRs, e com o modelo do próprio perfil). O servidor recusa o que a fase não pode usar (`stage_executor_unsupported`).
- **Como cada fase usa a escolha.** Os documentos são escritos pelo backend: o executor do projeto vem antes do padrão das Configurações, e o que você escolher para uma rodada no seletor "Modelos" do estúdio vale mais que os dois. Code, QA e PRs partem da escolha nos seletores da própria fase, onde ainda dá para trocar antes de rodar; sem escolha seguem o padrão. Se o executor salvo não serve mais (perfil sem credencial, Codex que o Harflex não segura), a página da fase diz que parte do padrão e o cartão mostra “N indisponíveis”; um documento (Discovery, SPEC, Plan) nessa situação não troca de modelo em silêncio: a rodada para e a tela nomeia a fase e onde ajustar. O cartão também avisa quando o catálogo não lista mais o modelo salvo, e, se as escolhas não puderem ser lidas, mostra o aviso fora do cartão (visível mesmo recolhido), com “Tentar de novo”.
- **Pipelines antigos.** Os que ainda usam o fluxo de preparação sem conversa mantêm os seletores próprios de Spec e Plan; para eles o cartão vale para Code, QA e PRs.

## Fim do pipeline: QA e pull requests

A barra do topo mostra **Discovery, SPEC, Plan, Code, QA e PRs**. QA é a avaliação independente que antes aparecia como Eval (o identificador interno continua `eval`). Enquanto uma etapa que tem sessão própria (Code, QA e PRs) está ativa, a barra segue essa sessão em vez de repetir “Em andamento”: **IA trabalhando**, **Aguardando autorização**, **Executado · verificar** (Code), **Executado · registrar** (QA), **Executado · concluir** (PRs) ou **Execução falhou**. A etapa só muda para “Aguardando decisão” ou “Concluído” depois que você verifica o resultado na página Pipelines.

Aprovar o QA não encerra mais o pipeline: ele passa para **PRs**, o último passo. O patch aprovado continua sendo aplicado à pasta do projeto por uma ação separada e conferida; o painel de PRs só libera a IA depois disso, porque ela trabalha nessa pasta. Em **Abrir PRs com a IA** você escolhe o perfil de API (o modelo é o do perfil, como em qualquer conversa, a menos que a fase PRs tenha um modelo escolhido em **Provedor e modelo por fase**: então a conversa fica presa a ele, confirmado no catálogo), e o Harflex abre uma conversa comum do projeto (com terminal, arquivos e as ferramentas MCP conectadas) vinculada ao pipeline, com um pedido que traz o plano aprovado e os critérios que o QA conferiu: ver o estado do Git, criar uma branch `harflex/<resumo>`, fazer o commit só do que pertence ao trabalho, enviar a branch e abrir o PR pelo GitHub ou Bitbucket, sem push forçado, sem merge e sem apagar branches. Perfis de CLI não servem aqui, porque o terminal e o MCP rodam no Harflex. Na conversa vale a permissão do projeto: em **Acesso total** a IA trabalha sem interrupções; nos outros perfis cada comando e chamada MCP pede a sua aprovação, e o painel oferece o menu de permissões ali mesmo.

Quando a IA termina, **Concluir PRs** guarda a resposta final dela como evidência da etapa (o relatório com os links dos PRs aparece no pipeline) e encerra o pipeline; só vale se a última execução da conversa terminou com sucesso. **Pular os PRs** encerra o pipeline registrando a etapa como pulada, com um motivo opcional. Até oito conversas por pipeline. Pipelines salvos antes desta etapa terminaram no QA e ficam com PRs pendente; o painel também os atende, e pular ou concluir os encerra do mesmo modo.

## Nada trava no fim da tarefa

Terminar uma execução não tranca a conversa, e terminar o pipeline não impede de seguir trabalhando.

- **Code e QA com API.** A conversa do Code continua aceitando mensagens depois que o run termina, até você **verificar o código**; verificar a fecha, porque o patch avaliado não pode mudar depois. A conversa do QA que ainda não rodou aceita o pedido; depois do veredito ela não continua. A escolha de modelo de uma sessão não expira mais: antes de cada mensagem o Harflex confere o estado atual (perfil, credencial, catálogo ainda listando o modelo), não a idade da escolha, então esperar uma aprovação ou voltar horas depois não derruba a conversa.
- **Conversa que não pode ser retomada** (run de CLI que acabou, Code já verificado, QA com veredito, provedor que sumiu). A caixa de mensagem continua ativa. Ao enviar, o Harflex abre um novo chat e leva o contexto: no mesmo backend se ele ainda serve (uma API, ou um CLI cujo modelo padrão o catálogo dele confirma), senão nos seus provedores de costume, cada um tentado em ordem, então um catálogo que não confirma o modelo ou um provedor que recusa não deixam você parado. Se a conversa foi fechada enquanto estava aberta (você verificou o Code na página Pipelines, o provedor mudou), a tela percebe ao voltar a ela ou na primeira mensagem e passa a continuar em um chat novo. O que vai junto é o primeiro pedido, os arquivos que a conversa alterou, o aviso de que o patch ainda não foi aplicado (quando é o caso) e a última resposta do agente, marcados como referência e não como instrução; a saída das ferramentas não é copiada (a resposta do agente pode citá-la). O motivo registrado no chat novo traz o ID da conversa de origem. O chat novo é um chat comum do projeto, com a permissão do projeto: os limites de ferramentas de um agente personalizado não passam para ele. A mensagem mostra só o que você escreveu e deixa o contexto dobrado, e o chat novo leva o nome do seu pedido. O texto fica na caixa até aparecer no histórico, então uma falha ao abrir o chat ou ao enviar não o perde. **Continuar em novo chat**, no alto, continua existindo e só prepara o último pedido para você revisar.
- **Os PRs.** A conversa dos PRs é um chat comum do projeto (aparece na lista como “PRs · título do trabalho”) e fica aberta depois de **Concluir PRs**. Quando o revisor pedir ajustes, o relatório final do pipeline oferece **Corrigir os comentários da revisão**, que abre essa conversa com um pedido pronto na caixa (ler os comentários dos PRs, corrigir na mesma branch de cada PR, commit e push sem push forçado, responder a cada comentário resolvido), e **Continuar a conversa dos PRs**, que só a abre. Nada é enviado sozinho. Como a IA mantém o contexto, o terminal e o MCP, é ali que os fixes saem.
- **Outra tarefa.** Novo trabalho e Novo chat ficam disponíveis sempre que não houver uma execução em andamento; nada precisa ser concluído antes. Um rascunho que você não enviou precisa ser enviado ou descartado primeiro, para não se perder. Uma conversa encerrada com uma aprovação que ninguém mais pode dar não conta como execução em andamento.

## Segurança e limites

O catálogo guarda somente referências de credenciais; chaves ficam no cofre do sistema. A publicação do perfil e de sua referência histórica ocorre na mesma transação SQLite. A migração preserva as referências ativas existentes; versões publicadas depois dela continuam no inventário após rotação. A UI mantém a chave apenas no campo não controlado e o limpa após envio. Erros da fachada são sanitizados; o MarshalError controla somente `cause`, e o Wails serializa separadamente a mensagem externa.

Cada sessão de API captura a credencial autorizada para aquele backend e remove suas ocorrências dos valores de conteúdo dos eventos antes de persistir ou emitir, incluindo prompts, mensagens, diffs, resultados de ferramentas e argumentos de aprovação. Deltas do assistente e atualizações de ferramentas retêm uma cauda limitada para reconhecer chaves e UTF-8 divididos em fragmentos. Cada chamada de ferramenta tem seu próprio buffer, compartilhado entre stdout/stderr porque a UI concatena esses fluxos; a cauda é publicada antes do encerramento da chamada ou execução. Prefixos incompletos da chave são ocultados de forma conservadora ao finalizar o buffer.

IDs internos de chamadas e aprovações são substituídos por aliases públicos opacos consistentes no journal e nas respostas. A fachada traduz uma aprovação pública válida de volta ao ID privado; aliases consumidos ou desconhecidos são recusados. Reutilizar um ID interno em outra ocorrência gera outro alias. A política de eventos ao vivo preserva apenas aliases conferidos no registro da sessão e valores limitados de enumerações geradas pelo aplicativo. Nomes de ferramentas, tipos e outros textos fornecidos pelo modelo passam por redação, assim como conteúdo, argumentos e detalhes; a execução interna mantém os valores originais. Os mapas de aliases ficam apenas em memória durante a sessão e são descartados no encerramento; recuperação após reinício invalida aprovações pendentes. O snapshot impede que uma sessão antiga use a chave de outro perfil ou revisão. Os buffers de credenciais são zerados no encerramento drenado do serviço; cópias transitórias em strings Go e bibliotecas não têm garantia de apagamento físico.

A exportação de auditoria gera JSONL, com um evento por linha, no caminho escolhido pelo usuário. Ela também remove credenciais cujas referências publicadas ainda possam ser resolvidas no cofre, incluindo versões anteriores. Todos os valores textuais do payload são redigidos na exportação, inclusive IDs e nomes históricos; apenas as chaves JSON e o envelope do evento são preservados. Uma referência já apagada é ignorada; outras falhas do cofre interrompem a exportação. Isso não reescreve journals antigos nem recupera chaves históricas desconhecidas, apagadas ou rotacionadas antes do inventário. A proteção na persistência cobre somente a credencial conhecida da sessão: segredos arbitrários inseridos pelo usuário, presentes em arquivos, codificados ou obtidos por CLIs externos exigem revisão do conteúdo e isolamento apropriado. CLIs externos não recebem a credencial do backend de API e administram suas próprias credenciais. Journals e diffs ainda podem conter conteúdo sensível: mantenha o diretório de dados sob proteção do usuário e revise antes de compartilhar.

Ferramentas de arquivo resolvem caminhos no workspace e aplicam política de risco. Shell e CLIs externos executam com os privilégios do usuário: **não são sandbox** e podem acessar arquivos e rede além do workspace. A configuração de permissões do próprio CLI continua relevante; a política do Harflex não equivale a interceptar todas as ações internas de um agente externo.

Falhas esperadas de uma ferramenta voltam ao modelo como resultado da chamada e a execução continua: arquivo ou pasta inexistente, edição cujo trecho não aparece exatamente uma vez, argumentos inválidos, arquivo binário ou grande demais para ler de uma vez, comando com código de saída diferente de zero e comando que estoura o próprio limite de tempo. O journal guarda um código e uma frase escritos pela própria ferramenta (`recoverable: true`), nunca o texto do erro bruto, que pode trazer caminhos privados ou segredos, e a tela explica em português o que houve. Qualquer outro erro, tentar sair da pasta do projeto, ferramenta desconhecida, política que nega e cancelamento continuam encerrando a execução, com um código seguro no journal; o limite de turnos e de chamadas impede que o modelo repita o mesmo erro para sempre.

Por padrão, o shell recebe uma allowlist de variáveis do sistema. Não herda variáveis de proxy, JAVA, GOPATH ou AWS, nem chaves de provedores do processo do harness. `Env: nil` seleciona essa lista; `Env: []string{}` passa ambiente vazio; valores explícitos substituem a herança. HOME, diretórios XDG, SSH_AUTH_SOCK e perfis do shell de login podem reintroduzir configurações, credenciais e acesso: o filtro reduz vazamento acidental, não isola o processo nem garante ausência de segredos. Ferramentas que dependem de variáveis omitidas exigem configuração explícita.

Prompts aceitam até 1 MiB em bytes; excedentes são recusados antes de journal/execução, tanto para API quanto para agente externo. Resultados de ferramenta têm até 10 segundos para persistência, acomodando o payload máximo; os demais eventos mantêm o prazo de 2 segundos. Saída, timeout e cancelamento têm limites próprios; cancelamento não desfaz efeitos já executados.

O backend expõe `ListSessions` por workspace e `OpenSession` idempotente. Abrir uma sessão não chama o provedor nem executa ferramentas: reconstrói histórico validado do journal, com leitura incremental limitada a 64 MiB por histórico e 34 MiB por payload serializado (16 MiB de conteúdo, 16 MiB de detalhes e 2 MiB de margem para envelope/encoding), com o mesmo limite no writer e no reader e verificando tamanho antes de carregar o BLOB, e pares completos de chamadas/resultados. Conteúdo redigido permanece redigido no próximo prompt. Recuperação fecha chamadas sem resposta e o run na mesma transação. Sem evidência `tool.called`, grava `tool.skipped` com `not_executed`; com essa evidência e sem resultado, grava `tool.failed` com `outcome_unknown`, pois os efeitos podem ter ocorrido. Nenhuma ferramenta é executada novamente. Journals antigos que já possuem `run.interrupted` recebem apenas os resultados sintéticos faltantes, sem duplicar o terminal; aprovações anteriores nunca voltam a ser executáveis. Se a recuperação do startup tiver sido omitida, `OpenSession` recupera esse registro antes de admiti-lo e pode emitir apenas esses eventos duráveis de fechamento. Após a recuperação normal, abrir não adiciona eventos. Cada append verifica também o total de 64 MiB do stream sob a mesma transação e lock de escrita, incluindo reparos de recuperação. Ao atingir o limite, o run é selado sem afirmar um terminal não persistido. Streams legados acima do orçamento ficam com status `history_too_large`: permanecem no catálogo, sua abertura é recusada com erro seguro e as demais sessões continuam a recuperação. Erros reais de banco continuam bloqueando o startup. A soma de bytes usa uma consulta O(n) por append nesta fundação; uma projeção/contador transacional fica para uma otimização posterior. A exportação de auditoria também mantém o orçamento de leitura e recusa legados excessivos. O status do catálogo acompanha os eventos duráveis e é reconciliado após falhas. Sessões novas guardam um fingerprint da revisão do backend, sem a chave; sessões antigas usam a data da revisão como verificação conservadora. Backends removidos ou alterados continuam listáveis e o histórico pode ser aberto para consulta; novas mensagens são recusadas com o motivo de indisponibilidade ou alteração do backend, sem construir provedor ou consultar credenciais.

Prompts de CLI também ficam no journal, depois do evento durável de início do run; o processo só é iniciado após ambos. Falha ao persistir o prompt tenta fechar o run com um terminal seguro e sela o runner. Em testes/ambientes com adaptador OpenCode explicitamente injetado, a retomada só ocorre após capturar um ID de sessão válido da saída estruturada; sem esse ID, um segundo prompt exige uma sessão nova, mas o histórico permanece acessível. O campo `resumable` considera backend disponível e revisão compatível; para OpenCode já utilizado, também exige o binding durável válido. A disponibilidade é uma leitura momentânea e o executável pode desaparecer entre listar e abrir. Codex sempre informa `resumable=false`: uma sessão ainda não utilizada pode ser aberta para sua única execução; sessões utilizadas abrem para consulta e recusam novos prompts. Eventos e texto externos continuam preservados para replay; autenticação e dados internos permanecem sob responsabilidade do CLI. A UI lista sessões recentes, permite abrir o histórico sem execução automática e distingue sessões retomáveis, somente leitura e a primeira execução isolada. A exportação JSONL fica em Artefatos e respeita o mesmo orçamento de leitura; históricos legados acima do limite permanecem armazenados, mas não podem ser reabertos nem exportados pela aplicação.

O adaptador de `codex exec --json` projeta `item.completed` de `agent_message` e captura `thread.started.thread_id` para auditoria. O adaptador de `opencode run --format json` projeta `text` com `part.type=text`, lê `part.text` e captura `sessionID` da raiz ou da parte. Snapshots idênticos não duplicam a conversa. Qualquer snapshot diferente posterior substitui a mesma parte com o texto completo, inclusive texto menor ou vazio; uma resposta esvaziada desaparece da conversa, mantendo o evento no journal para replay. A ordem do JSONL é a referência e o formato completo preserva a redação de credenciais. O estado de normalização pertence a cada execução. Eventos desconhecidos e logs ficam em Eventos, sem virar respostas do assistente. As [fixtures de protocolo](internal/externalagent/testdata/README.md) são sintéticas, baseadas nos formatos oficiais, e ligam subprocesso local, journal e replay visual; não representam validação de autenticação ou execução contra provedores reais.

Dados do pipeline/atividade de demonstração e fixtures não representam custo, status ou desempenho real. Não use screenshots sintéticos como evidência de provedor ou produção.
